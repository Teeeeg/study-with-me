# GPU调度问题

Kubernetes 默认调度器将 GPU 视为标量资源（`nvidia.com/gpu: 1`），这对单 GPU 作业足够，但面对 AI 集群真实负载存在三个致命盲区：**GPU 碎片化、拓扑不感知、Gang Scheduling 缺失**。

## GPU 调度三大问题总览

| 问题 | 现象 | 根本原因 | 影响 | 解决方案 |
|------|------|---------|------|---------|
| **GPU 碎片化** | 4 张空闲 GPU 无法分配给 4-GPU 任务 | 调度器视 GPU 为标量，不保证连续分配 | Pod 启动失败或性能极差 | 装箱优化 + Bin Packing |
| **拓扑不感知** | 分配的 GPU 通信路径是最差的 | 调度器不知道 NVLink/PCIe 拓扑 | 训练时间增加 2-5 倍 | 拓扑感知调度器 |
| **Gang Scheduling 缺失** | 7 个 Pod 占 GPU 等待第 8 个 | 逐个调度 Pod，不考虑任务整体 | GPU 空转，资源死锁 | Volcano/Kueue 原子调度 |

**核心矛盾**：调度器把 GPU 当成标量资源，但 GPU 实际上是**离散的、有拓扑关系的、需要协同的**设备。


## 问题 1：GPU 碎片化

### 4 张空闲 GPU ≠ 可以运行 4-GPU 任务

**场景**：
```
节点 A (8 GPU): [X][ ][X][ ][X][ ][X][ ]  ← 4 张占用，4 张空闲但不连续
节点 B (8 GPU): [ ][ ][ ][ ][ ][ ][ ][ ]  ← 8 张全部空闲
```

提交 4-GPU 训练任务：
- **默认调度器**：看到节点 A 有 4 张空闲 → 调度到 A
- **实际分配**：GPU 1,3,5,7（离散）
- **训练框架期望**：`CUDA_VISIBLE_DEVICES=0,1,2,3`（连续）
- **结果**：启动失败或性能极差

### 根本矛盾

- **调度器视角**：GPU 是可计数的标量
- **训练框架视角**：GPU 是有拓扑关系的设备（需连续 ID、NVLink 连接）
- **分配机制**：Device Plugin 按位图分配，不保证连续性

## 问题 2：拓扑不感知

### 分配的 GPU 通信路径可能是最差的

**GPU 通信性能差异**：

| 路径类型 | 带宽 | 适用场景 |
|---------|------|---------|
| NVLink 直连 | ~600 GB/s | 同 NVSwitch 域 |
| 同 CPU PCIe | ~32 GB/s | 同 NUMA 节点 |
| 跨 CPU PCIe | ~16 GB/s | 跨 NUMA |
| CPU 中转 | ~10 GB/s | 最差情况 |

**DGX A100 节点拓扑示例**：
```
GPU 0-3: NVSwitch 全互连（Domain 0）
GPU 4-7: NVSwitch 全互连（Domain 1）
跨域通信：需经 CPU，性能下降 10 倍

理想分配：[0,1,2,3] 或 [4,5,6,7]
差的分配：[0,2,4,6] ← 大量跨域通信
```

**默认调度器盲区**：
- 不知道 GPU 间 NVLink 连接
- 不知道 PCIe switch 拓扑
- 不知道 NUMA 亲和性

**影响**：训练时间可能增加 2-5 倍

## 问题 3：Gang Scheduling 缺失

### 分布式训练的 Pod 无法原子调度

分布式训练是 **All-or-Nothing** 任务：8-GPU 训练需要 8 个 Worker Pod 同时启动，缺一个其他 7 个都空转。

**场景**：
```
集群状态：
- 节点 A: 7 张 GPU 空闲
- 节点 B: 1 张 GPU 空闲

提交 8-GPU 训练（8 个 Pod）：
1. Pod 0-6 → 节点 A ✓（占用 7 张 GPU）
2. Pod 7 → 节点 B ✓（占用 1 张 GPU）
3. 训练初始化：等待所有 8 个 Worker 就绪
4. 死锁：7 个 Pod 等待第 8 个，但资源不足
5. 7 张 GPU 空转，资源浪费
```

**默认调度器行为**：
- 逐个调度 Pod，不考虑任务整体
- 可能导致部分调度成功，部分失败
- 已调度的 Pod 占用 GPU 但无法工作

# 基础设施层

## Kubernetes GPU 管理的难点
| 痛点 | 具体表现 | 业务影响 | 当前方案 | 局限性 |
|------|---------|---------|---------|--------|
| **GPU 可见性差** | 无法查看 GPU 型号、显存、利用率 | 资源盲调，无法按需分配 | Node labels 手动标注 | 不准确，不实时 |
| **无法共享 GPU** | 1 张卡只能分配给 1 个 Pod | 推理场景利用率 <5% | MIG/MPS/Time-slicing | 配置复杂，隔离不完善 |
| **显存无法限制** | Pod 可以用满整张卡显存 | OOM 导致节点上所有 Pod 崩溃 | 无原生支持 | 需要自定义 Device Plugin |
| **故障 GPU 仍调度** | 坏卡节点继续接收 Pod | Pod 启动失败，反复重试 | Node taint 手动标记 | 响应慢，需人工介入 |
| **无资源优先级** | 训练和推理抢 GPU | 在线服务被批量任务挤占 | PriorityClass | 不感知 GPU 特性 |
| **跨节点通信慢** | 多节点训练通过网络通信 | 10× 慢于 NVLink | NCCL 自动选择路径 | K8s 调度不感知网络拓扑 |
| **GPU 利用率低** | 单任务无法充分利用 GPU | 算力浪费，成本高 | 批处理、模型并行 | 需应用层优化 |
| **缺少配额管理** | 无法按团队限制 GPU 使用 | 资源被少数任务占用 | ResourceQuota | 只能限制数量，不限时长 |
